# NH Portfolio

[![CI](https://github.com/gmdjlee/nh_portfolio/actions/workflows/ci.yml/badge.svg)](https://github.com/gmdjlee/nh_portfolio/actions/workflows/ci.yml)

NH투자증권 나무 계좌의 보유 종목과 자산 비중을 보고, 목표 비중을 입력하면
매수/매도해야 할 주식 수를 계산해 주는 개인용 Android 앱. **거래 기능은 없다.**

## 빌드

```bash
export JAVA_HOME="/c/Program Files/Android/Android Studio/jbr"   # 또는 다른 JDK 21
./gradlew assembleDebug
./gradlew ktlintFormat ktlintCheck detekt testDebugUnitTest
```

compileSdk 37 이 필요하다. 없으면 `sdkmanager "platforms;android-37"` 로 설치한다.

## 설정

1. <https://www.nhplug.com> 에서 앱 키(appkey)와 시크릿(appsecretkey)을 발급받는다.
2. 앱 최초 실행 시 6자리 PIN 을 만든다. 지문을 등록할 수 있으면 등록을 제안한다.
3. 설정 화면에 앱 키와 시크릿을 입력하고 저장한다. 저장한 값은 다시 보이지 않는다.

운영(실계좌) 환경만 쓴다. 모의투자 계좌(acct_type 03)는 목록에 나오지 않는다.

## 보안 — 위협 모델

무엇을 막고 무엇을 못 막는지 정확히 적는다.

| 상황 | 결과 |
|---|---|
| DataStore 파일만 복사 (백업·adb·다른 앱) | **오프라인 공격 불가.** PIN 을 감싸는 HMAC 키가 AndroidKeyStore 를 떠나지 못한다. |
| 루팅된 기기 + 기기 잠금 해제 상태 + 앱은 잠김 | 상한은 **10⁶ 회의 Keystore HMAC 호출** (TEE 약 20분~3시간(추정), StrongBox 약 1~2일(추정) — 실기기로 측정한 값이 아니다). PBKDF2 는 salt·반복수가 파일에 있어 오프디바이스로 미리 계산되므로 상한이 아니다. **앱 자체의 PIN 잠금(5회부터 30초 배증, 상한 1시간)도 상한이 아니다** — 실패 횟수가 공격자가 이미 쥐고 있는 그 DataStore 파일 안에 있어서, 값을 되돌려 쓰면 그대로 재시도할 수 있다. 이 시나리오에서 실제로 시도 속도를 늦추는 건 Keystore HMAC 호출 지연뿐이다. |
| 기기 자체가 잠긴 상태 | `setUnlockedDeviceRequired` 가 HMAC 키 사용을 막는다. |
| 앱 잠금이 풀린 동안의 메모리 덤프 | **전부 노출된다.** 이 앱이 막을 수 있는 범위가 아니다. |
| 지문 우회 시도 | 불가능. CryptoObject 의 **출력이 곧 DEK** 라 인증 성공 여부(boolean)를 속여도 얻는 게 없다. |
| 화면 캡처·최근 앱 썸네일 | `FLAG_SECURE` 로 차단. |
| 오버레이를 통한 탭재킹 | `setHideOverlayWindows` + `filterTouchesWhenObscured` 로 차단. |
| 클라우드 백업·기기 이전 | `allowBackup=false` + `dataExtractionRules` 로 전부 제외. |
| 루팅 탐지 | **하지 않는다.** 우회 가능하고 Keystore 결속 이상의 이득이 없다. |
| NH 서버가 보낸 오류 문구 | **그대로 화면에 표시된다** (`rsp_msg`). 신뢰 경계는 TLS 로 검증된 NH 서버까지다 — 앱 키·계좌 정보가 요청 본문에 없으므로 되돌아올 수 없고, Compose `Text` 라 마크업도 실행되지 않는다. |

로그·화면·예외 메시지에 앱 키·시크릿·토큰을 절대 넣지 않는다. `ktor-client-logging`
의존성 자체가 없고, 앱 전체에서 `Log.*` 호출은 `NhApi.kt` 의 디버그 로그 한 줄
(`Log.d("NhApi", "$path rsp_cd=...")`, 업무 오류 코드/문구만 담고 비밀은 없음)이
전부다. `Log.i`/`Log.w`/`Log.e`/`Log.wtf` 호출은 앱 어디에도 없으므로, 릴리스
`proguard-rules.pro` 의 `Log.d`/`Log.v` 제거 규칙 하나가 앱 소스가 직접 호출하는 로그를
남김없이 덮는다. R8 로 축소한 릴리스 APK 의 dex 를 직접 열어 확인했다 — 아래
"릴리스 빌드 검증" 참고.

PIN 을 5회 틀리면 30초 잠기고 실패마다 두 배로 늘어난다(상한 1시간). 자동 초기화는
하지 않는다 — 실수로 데이터를 잃는 쪽이 더 나쁘다. PIN 을 잊었다면 복구할 방법이 없다. 안드로이드
설정 → 앱 → 저장공간 → 데이터 삭제로 지우고 처음부터 설정한다(앱 안의 "앱 초기화"는 잠금이
풀린 상태에서만 쓸 수 있다).

## 릴리스 빌드 검증

`assembleRelease`(R8 full mode, `isMinifyEnabled` + `isShrinkResources`)로 빌드하고,
디버그 키로 서명해 에뮬레이터(Pixel Fold, API 36)에 설치해 실행까지 확인했다 — 이
에뮬레이터 실행 확인은 커밋 `481c458` 기준이다. 아래 로그 제거 검증은 커밋 `6a7bf32`
기준으로 릴리스를 다시 빌드해 재확인한 결과다(두 커밋 사이의 변경은 로그·직렬화 경로에
영향이 없다). `lintVitalRelease` 는 이슈 없음. 자세한 절차와 증거는
`.superpowers/sdd/2026-08-30-nh-portfolio/task-13-report.md` 에 있다.

**로그 제거 확인 방법과 결과**: 릴리스 dex 를 문자열로 뒤져 `Log.d` 호출 흔적을
찾는 방법은 함정이 있다 — `Log.d("NhApi", "$path rsp_cd=...")` 는 태그와 메시지가
서로 다른 인수라서 `"NhApi rsp_cd="` 라는 하나의 상수는 어느 빌드에도 없다. 그
문자열을 찾는 검사는 항상 "깨끗함"으로 나오므로 아무것도 증명하지 못한다.

대신 로그 메시지 템플릿의 리터럴 조각(앞 공백과 `=` 가 붙은 `" rsp_cd="`, `rsp_cd`
필드명과는 다른 문자열)으로 디버그 빌드와 릴리스 빌드를 **같은 방법으로** 비교했다.

| 검사 대상 | 디버그(서명) dex | 릴리스(서명) dex |
|---|---|---|
| `" rsp_cd="` (로그 메시지 상수) | **있음** — `classes6.dex` | **없음** — R8 이 `Log.d` 호출과 그 메시지를 통째로 제거 |
| `rsp_cd` (SerialName, `=` 없음) | 있음 | **있음** — JSON 파싱에 필요해 살아남음 (증거: 같은 문자열이 사라지지 않는다는 대조군) |
| `NhApi` (태그·클래스명 등) | **있음** — `classes5/6/12.dex` | 없음 — R8 이 클래스명을 난독화 |

디버그 APK 는 `classes.dex` ~ `classes12.dex` 까지 12개 dex 로 나뉘어 있었다
(멀티덱스, 축소 없음) — `unzip -p ... classes.dex` 하나만 보면 실제로 로그가 담긴
`classes6.dex` 를 놓친다. 릴리스 APK 는 R8 이 전부 `classes.dex` 하나로 합친다.
두 경우 모두 **모든** dex 를 추출해 검사해야 한다.

## 기기 스모크 체크리스트 (릴리스마다 1회)

축소된 릴리스 APK 로 확인한다(디버그 빌드로는 R8 문제를 못 잡는다). 이 릴리스는
기본 OkHttp 엔진(Ktor `io.ktor:ktor-client-okhttp`)이 실제로 요청을 보내는 **첫**
검증이다 — 단위 테스트는 전부 Mock 엔진을 쓰므로, `NoClassDefFoundError` 나
프로바이더 누락 같은 문제는 여기서만 드러난다.

- [ ] 최초 실행 → PIN 설정 → 지문 등록 제안 → 설정 화면
- [ ] 앱 키 저장 → 계좌 목록 → 포트폴리오 (토큰 발급 횟수는 로그로 볼 수 없다 —
      필요하면 프록시로 `/oauth2/token` 요청 수를 센다. 단위 테스트가 1회를 보장한다)
- [ ] 앱을 껐다 켰을 때 토큰 재발급이 일어나지 않는다
- [ ] 나무 앱에서 수동 매매 → 1초 안에 스낵바 + 잔고 갱신 + 예수금 즉시 감소
- [ ] 5분 이상 무거래 유지 → 재연결 로그 0건 (WebSocket ping/pong)
- [ ] 목표 비중 입력 → 매수/매도 주식 수 표시, 합계 초과/미달 배지
- [ ] 화면 끄고 2분 후 복귀 → 잠금 화면
- [ ] 지문으로 잠금 해제 / 지문 재등록 후 PIN 으로 해제 + 재등록 안내
- [ ] PIN 5회 오입력 → 30초 잠금, 재부팅해도 잠금 유지
- [ ] 스크린샷 차단, 최근 앱 썸네일 가려짐
- [ ] 오버레이 앱(예: 화면 필터) 띄운 채로 실행 → 오버레이가 사라지고 터치가 먹지 않는다
- [ ] 비행기 모드에서 실행 → "네트워크 오류" (인증 실패가 아니어야 한다)
- [ ] 다크 모드 전환
- [ ] 잔고 응답에 **같은 종목코드가 두 번** 나오는지 확인 (신용/융자 보유, 해외/장내외
      분리 계좌 등에서 가능). 상품유형명(`pdt_tp_nm`)까지 같은 진짜 충돌이면 화면에 중복
      경고가 뜨는지, 다르면(예: 위탁·신용융자) 두 줄로 갈려 각자 목표를 따로 잡는지
      확인한다. (예전에는 이 경우 리밸런스 목표가 이중 계상됐으나, 신원을 `종목코드`에서
      `종목코드|상품유형명`으로 바꾸며 고쳤다 — 코드 확인 완료, 실기기 미검증.)
- [ ] 신용/융자 보유가 있으면 `lon_bnc_amt`(대출잔고금액)·`lon_byn_dt`(대출매수일자)가
      실제로 채워져 오는지 확인한다 — 비어 있으면 신용 배지가 하나도 안 붙는다.
- [ ] 현금성 자산(CMA·발행어음 등)으로 보이는 잔고 행의 `pdt_tp_nm` 이 실제로 무엇인지
      확인한다 — 지금은 확인된 값이 없어 사용자가 직접 지정하게만 해 두었다.
- [ ] 신용으로 산 종목을 상환하거나 위탁으로 갈아탄 뒤에도 `pdt_tp_nm` 이 그대로인지
      확인한다 — 저장된 목표 비중의 신원이 이 값이라, 바뀌면 그 목표가 고아가 되어
      조용히 자리를 잃는다("100%로 맞추기"를 눌러도 채워지지 않는다).
- [ ] 이번 업그레이드로 신원 체계가 바뀌면서 저장된 현금성 자산 지정도 함께 지워진다
      (옛 값을 새 신원에 매칭할 방법이 없어서다) — CMA·발행어음 행이 업그레이드 직후
      일반 종목처럼 보이는지, "현금성 자산으로 묶기"로 다시 지정해야 하는지 확인한다.
- [ ] 포트폴리오 화면에 들어간 뒤 65초 백그라운드 → 잠금 해제 후 **어느 화면으로
      돌아오는지** 기록 (백스택 유지 여부는 아직 확인되지 않았다)
- [ ] 표시되는 **주식수가 나무 앱과 정확히 일치**하는지 최소 한 종목에서 확인
      (API 가 Double 로 주고 Long 으로 변환한다)
- [ ] 수익률이 나무 앱과 같은 값인지 확인 (`pft_rt` 가 12.5 인지 0.125 인지 — 100배 틀리면 여기서 드러난다)
- [ ] 설정에서 지문 토글 → PIN 창이 뜨면 **취소 버튼으로 빠져나올 수 있는지** 확인
      (앱 잠금 화면 자체는 취소가 없어야 정상)
