## 2 앱에 옮길 계산 정의

`docs/manage/riskmodel.py`(원 코드), `riskmodel_functions.md`, `guide_stats.py` 를 근거로
확정한 정의다. 이 절이 `market/Breadth.kt` 의 사양이며, 단위 테스트는 이 절을 그대로 검증한다.

`riskmodel.py` 에는 신호가 여섯 개(`breadth`, `trend`, `drawdown`, `vol`, `fx`, `global`)
정의되어 있지만 **최종 모델은 `breadth` 하나만 쓴다.** 나머지는 보고서의 비교 전략이며
`guide_stats.py` 는 `_pct_rank`·`score_to_exposure`·`backtest` 만 가져온다. 환율과 S&P
데이터는 필요 없고, 이식 범위도 늘지 않는다.

입력은 유니버스 종목 집합 `U`(약 200종목), 종목별 일별 **수정** 종가 시계열, 거래일 달력이다.

1. **시장폭.** 이동평균 길이 `m ∈ {150, 200, 250}` 마다,
   - `MA(i, m, t)` 는 종목 `i` 의 최근 `m` 거래일 종가 평균이다. 유효 관측이 `floor(m × 0.75)`
     개 미만이면 미정의로 둔다(`min_periods`).
   - `breadth(m, t)` 는 `종가 > MA` 인 종목 수를, 종가와 MA 가 **둘 다** 정의된 종목 수로
     나눈 값이다.
   - 분모가 **30 미만이면 그 날은 미정의**로 둔다.
2. **백분위.** `_pct_rank` 는 `rolling(756, min_periods=252).rank(pct=True)` 다. 즉,
   - 창은 최근 **756개 행**이고, 그 안에서 정의된(미정의가 아닌) 관측만 센다. 그 수를 `n` 이라 한다.
   - `n < 252` 이면 미정의다. **252 이상 756 미만이면 부분 창으로 계산한다.**
   - `pct(m, t)` = `(현재값보다 작은 관측 수 + (현재값과 같은 관측 수 + 1) / 2) / n`.
     동점은 **평균 순위**로 처리한다(pandas 기본 `method='average'`). 시장폭은 `k / 유효종목수`
     라서 같은 값이 되풀이되므로 이 규칙을 빠뜨리면 재현이 안 된다.
   - 값의 범위는 `(0, 1]` 이다. 최솟값이어도 `1/n` 이지 0 이 아니다.
3. **평활.** `sm ∈ {20, 40, 60}` 마다 `smooth(m, sm, t)` 는 `pct(m, ·)` 의 최근 `sm` 개 평균이다.
   `sm` 개가 전부 정의되어 있을 때만 정의된다.
4. **구성별 양자화.** `q(m, sm, t)` = `round(smooth(m, sm, t) × 8) / 8`. 이것이
   `score_to_exposure(score, floor=0.0, cap=1.0, steps=8)` 이며, `floor=0` 이라 선형 변환은
   항등이 된다. **양자화는 여기서 한 번, 아래 6 에서 한 번 더, 모두 두 번 일어난다.**
5. **앙상블.** `ens(t)` 는 9개 `q` 의 산술평균이다.
6. **목표 비중.** `target(t)` = `round(ens(t) × 8) / 8`. 값은 0, 12.5, 25, …, 100% 중 하나다.
7. **판정.** `gap` 은 `target` 에서 **유지 비중**(§2.3)을 뺀 값이다. `backtest()` 의
   `abs(want − held) >= band` 그대로다.
   - `|gap| < 15%p` 이면 실행하지 않고 기록만 남긴다.
   - `gap < 0` 이면 당일 또는 익일에 **한 번에** 줄인다.
   - `gap > 0` 이면 3영업일 간격으로 **3회에 나누어** 늘린다.
8. **밴드.** `target` 기준으로 `[0, 13)` 최대 방어, `[13, 44)` 방어, `[44, 56)` 중립,
   `[56, 81.5)` 적극, `[81.5, 100]` 최대 투입이다.

### 2.1 반올림은 은행가 반올림이다

4 와 6 의 `round` 는 `np.round` 이며 **0.5 를 짝수 쪽으로 보낸다**(round-half-to-even).
Kotlin 에서는 `kotlin.math.round(Double)` 이 같은 규칙이고, `roundToInt()` 는 0.5 를 항상
올리므로 **쓰면 안 된다.** `riskmodel_functions.md` 의 표가 그대로 테스트 벡터다.

| `score` | `score × 8` | `np.round` (채택) | `roundToInt` (오답) |
|---|---|---|---|
| 0.0624 | 0.499 | 0.000 | 0.000 |
| **0.0625** | **0.500** | **0.000** | 0.125 |
| 0.0626 | 0.501 | 0.125 | 0.125 |
| 0.1875 | 1.500 | 0.250 | 0.250 |
| **0.3125** | **2.500** | **0.250** | 0.375 |

6 의 양자화에서는 정확한 0.5 가 나올 수 없다(9개 `k/8` 의 평균에 8 을 곱하면 `Σk/9` 이고,
그 소수부는 `.5` 가 되지 않는다). 그러나 4 의 양자화에서는 평활값이 `1/16` 의 홀수 배에
정확히 걸릴 수 있으므로 규칙이 실제로 갈린다.

### 2.2 워밍업을 지어내지 않는다, 부분 창은 드러낸다

`guide_stats.py` 는 평활 결과에 `.bfill().fillna(.5)` 를 걸어 백테스트가 첫날부터 시작되게
한다. `riskmodel_functions.md` 가 확인해 주듯 "해당 구간은 성과 집계에서 제외하므로 결과에
영향을 주지 않는" 백테스트용 장치다. **앱은 이 보정을 옮기지 않는다.** 실사용에서 같은
처리를 하면 "데이터가 모자라서 모르는 상태"가 "비중 50%" 라는 구체적인 지시로 둔갑한다.

반면 `min_periods=252` 의 **부분 창은 원 코드의 정의 자체이므로 그대로 옮긴다.** 다만 검증
기간은 워밍업 1,200일을 제외한 뒤라 그 구간의 창은 항상 756개가 차 있었다. 부분 창으로
계산한 값은 정의상 옳지만 검증된 조건은 아니므로, 창이 756개를 채우지 못하면 카드에
**"백분위 창 N/756일"** 을 표시해 그 사실을 감추지 않는다.

### 2.3 유지 비중 — 판정의 비교 대상

`backtest()` 는 목표를 **마지막으로 실행한 목표**(`held`, 1/8 격자값)와 비교하지, 가격
변동으로 흘러간 실제 비중과 비교하지 않는다. 가이드북 상단 막대의 "유지 비중 25% · 모델 목표
12.5% · 차이 12.5%p → 실행하지 않습니다" 도 같은 방식이다.

목표가 12.5%p 격자 위에 있으므로 이 규칙은 사실상 **"목표가 두 단계(25%p) 이상 움직였을 때만
실행"** 이다. 실제 비중과 비교하면 드리프트 2~3%p 만으로 한 단계 움직임(12.5%p)이 15%p 를
넘어, 검증된 것보다 두 배 가까이 자주 매매하게 된다. 그래서 **비교 대상은 유지 비중이다.**

앱에서 유지 비중은 `100% − 예수금 목표` 다. "이 목표로 맞추기" 가 예수금 목표를
`100% − 모델 목표` 로 잡으므로 적용 직후 유지 비중은 모델 목표와 같고, 다음 판정은 모델이
두 단계 움직일 때까지 "실행하지 않습니다" 가 된다. 새 저장소는 필요 없다. 예수금 목표가
아직 없으면(한 번도 적용한 적이 없으면) 실제 비중으로 대신하고 그 사실을 카드에 적는다.

가격 변동으로 생긴 드리프트는 이 판정의 대상이 아니다. 백테스트는 비중이 일정하게 유지된다고
가정했고, 실제 드리프트는 기존 목표 비중 화면의 매수/매도 수량에 이미 나타나므로 사용자가
따로 판단한다. 실제 비중은 카드에 참고값으로만 보여 준다.

### 3.2 없는 것: 랭킹·종목마스터·지수

krstock 31개 엔드포인트를 전수 확인했고 common 은 토큰 발급과 계좌목록 둘뿐이다.
주문 8개, 조회 12개, 시세 11개 가운데 **종목을 나열해 주는 것은 `etfComponents` 하나뿐이다.**
시가총액 상위 N 을 뽑는 랭킹 API 도, 코스피 지수 시세도 없다.

그래서 유니버스는 ETF 구성종목으로 조달한다. 이것이 KIS 없이 NH 만으로 끝낼 수 있는
유일한 경로이며, 동시에 **분기 유니버스 갱신을 사람 손 없이 처리하는 경로**이기도 하다.

## 4 유니버스 결정과 그 결과

**KODEX 200(069500)의 구성종목을 유니버스로 쓴다.** 2026-09-05 에 확정했다.

원 모델은 "코스피 시가총액 상위 250종목"을 썼다. 코스피200 은 시가총액 외에 유동성과
업종 배분 기준이 섞여 있어 상위 250 과 완전히 같지 않다. 이 차이가 만드는 결과는 셋이다.

1. **원지표(200일선 상회 비율)의 절대 수준이 조금 달라진다.** 그래서 가이드북 9절의
   검증값(2026-09-04 상회비율 41.5%, 3년 백분위 9.9%)을 그대로 재현할 수는 없다.
   대신 계산 파이프라인 자체는 합성 데이터로 만든 골든 벡터로 검증한다.
2. **백분위를 쓰기 때문에 영향이 크게 줄어든다.** 최종 신호는 절대 수준이 아니라 "최근 3년
   분포에서의 상대 위치"다. 유니버스가 조금 달라져 상회 비율이 전 구간에서 비슷하게
   평행이동하면 백분위는 거의 그대로다. 원 보고서가 절대 수준 대신 백분위를 고른 이유가
   바로 구조적 편향에 덜 민감하기 때문이라고 적혀 있다.
3. **분기 갱신이 자동으로 된다.** 가이드북 8절은 "분기 1회 유니버스 갱신(시가총액 상위
   250종목 재선정)"을 운영 작업으로 지시한다. ETF 정기변경을 따라가면 이 작업이 사라진다.

한 가지를 분명히 해 둔다. **유니버스가 바뀌면 과거 시장폭도 함께 다시 계산된다.**
원 파이썬 코드도 매 실행마다 현재 유니버스로 전체 이력을 다시 계산하므로 동작이 같다.
즉 이 모델의 시장폭 이력은 언제나 "오늘의 유니버스로 소급한 값"이며 실시간으로 관측된
값이 아니다. 백테스트도 같은 조건에서 검증되었으므로 일관성은 유지된다.

## 5 데이터 비용과 저장

### 5.1 얼마나 필요한가

백분위 창이 가득 차려면 756개의 시장폭 관측이 필요하고, 시장폭 하나를 정의하려면 종목마다
최대 250거래일의 종가가 필요하다. 여기에 60일 평활이 더해진다.

```
가득 찬 창:  250 (최장 MA) + 756 (백분위 창)      + 59 (최장 평활) ≈ 1,065 거래일
최소 조건:   187 (MA250 × 0.75) + 252 (min_periods) + 59 (최장 평활) ≈   500 거래일
```

**종목당 1,100거래일(약 4.4년)** 을 요청 기준으로 잡는다. 500일 이상만 확보되면 원 코드의
정의대로 부분 창 신호가 나오되, 창이 756개를 채우기 전까지는 카드에 "백분위 창 N/756일"
이 붙는다(§2.2).

### 5.2 호출 횟수와 통신량

| 작업 | 호출 | 통신량 | 소요 시간(초당 5회 기준) |
|---|---|---|---|
| 최초 백필 | 유니버스 1회 + 종목당 1~2회, 약 **200~400회** | 약 **30 MB** | **2~5분** |
| 주간 갱신 | 종목당 1회(`array_cnt=10`), 약 **200회** | 약 1 MB | 약 1분 |
| 분기 유니버스 갱신 | 1회 + 신규 편입 종목만 백필 | 수 MB | 수십 초 |

최초 백필은 통신량이 크므로 **Wi-Fi 를 권하는 안내와 진행률 표시, 중단 후 재개를 반드시
갖춘다.** 자동으로 다시 실행되어서는 안 된다.

### 5.3 저장

종목별 종가 1,100개를 `Int` 로 보관하면 200종목에 **약 1 MB** 다. 실제 저장 형식은 JSON
텍스트라 3~4 MB 에 가깝지만, 계산 비용의 논지는 같다. 이 정도면 매 실행마다
전체 이력을 다시 계산해도 계산 시간이 100 ms 를 넘지 않는다. 이동평균은 이동합으로,
백분위는 창 안 비교로 계산하면 총 300만 회 수준이다.

그래서 **증분 갱신 상태기계를 만들지 않는다.** 종가 배열만 파일에 두고, 화면을 열 때마다
파이프라인 전체를 처음부터 다시 계산한다. 옮겨야 할 상태가 없으니 틀릴 곳도 없고, 원
파이썬 코드의 동작과도 정확히 같아진다.

**저장 위치는 기존 DataStore 와 분리한다.** DataStore Preferences 는 `edit {}` 한 번마다
파일 전체를 다시 쓴다. 그 파일에는 비밀과 목표 비중이 들어 있고 토큰 재발급마다 쓰기가
일어나므로, 1 MB 짜리 종가 배열을 같이 넣으면 상관없는 설정 변경 하나가 매번 그 전체를
다시 쓰게 된다. 앱 전용 디렉터리(`filesDir/market/`)에 **종목별 파일**(`bars/<종목코드>.json`)과
유니버스 파일(`universe.json`)로 둔다. 파일 하나에 모으면 백필 중 종목마다 수 MB 를 다시 쓰거나,
끝에 한 번만 써서 프로세스가 죽으면 전부 잃는다. 종목별 파일은 재개·부분 실패·손상 격리가
저절로 된다(구현 중 확정, 2026-09-05).

**봉인하지 않는다.** 공개 시장 데이터이고 계좌·보유 정보가 전혀 들어 있지 않다. 목표
비중을 평문 DataStore 에 두는 기존 방침과도 일관된다. 봉인하면 DEK 가 필요해져 저장
경로가 잠금 상태에 묶이는데, 그렇게 해서 얻는 것이 없다.

## 6 정확도를 깨뜨릴 수 있는 곳

### 6.1 수정주가 — 스스로 검사해 보정한다

`period` 응답이 수정주가인지 원주가인지 명세에 적혀 있지 않다. 원주가라면 2:1 액면분할
종목의 종가가 하루 만에 절반이 되어 **200일 동안 이동평균 아래에 잘못 머문다.** 종목 하나가
시장폭을 0.5%p 흔들고, 분할이 몰린 시기에는 밴드가 통째로 어긋난다.

`prtt_rate`(락비율)의 단위가 확인되지 않았으므로 그 값에 기대지 않는다. 대신 응답에 반드시
들어 있는 두 필드로 배율을 직접 만든다.

```
락이 있는 날 t 의 보정 배율 = stck_sdpr(t) / stck_prpr(t−1)
                              ( 기준가 ÷ 전일 종가 )

적용 조건: fcam_mod_cls_code 가 01 액면분할 · 02 액면병합 · 03 주식분할 · 04 주식병합 중 하나이거나
          flng_cls_code 가 01 권리락 · 04 권배락 · 06 권리중간배당락 · 07 권리분기배당락 중 하나이고,
          |배율 − 1| > 0.02 인 경우
t 이전의 모든 종가에 이 배율을 곱한다(최신에서 과거 방향으로 누적).
```

이 방식은 **응답이 이미 수정주가인 경우를 스스로 걸러낸다.** 수정주가라면 전일 종가가 이미
나뉘어 있어 배율이 1 에 붙고, `|배율 − 1| > 0.02` 조건에서 그대로 통과한다. 따라서 실계좌
확인을 기다리지 않고 지금 구현할 수 있으며, 두 경우 모두 옳은 값이 나온다.

순수 배당락(`flng_cls_code` 02·03·05)은 **보정하지 않는다.** 원 모델이 쓴
FinanceDataReader 의 수정주가가 배당을 반영하지 않으므로, 반영하면 오히려 어긋난다.

종가가 무효해 버려진 봉이 권리락 전날이면 분모는 '직전 거래일'이 아니라 '직전에 남은 봉'이다.
배율 오차가 그 종목의 전 이력에 균일하게 곱해지므로 상회 판정은 거의 바뀌지 않는다.

### 6.2 상장 기간이 모자란 종목

ETF 구성종목 중에는 4년 전에 상장되지 않은 종목이 있다. `min_periods`(m × 0.75) 와 분모 30
하한이 이 경우를 흡수한다. 원 파이썬 코드와 같은 처리이며, 이 두 규칙을 빠뜨리면 상장 초기
종목이 전부 "이동평균 위"로 잡혀 시장폭이 부풀려진다.

상장폐지된 종목은 다음 유니버스 갱신(최대 90일)까지 마지막 종가가 채워진 채 분모에 남는다.
원 코드는 매 실행마다 유니버스를 다시 뽑아 이 구간이 없었다.

### 6.3 거래일 정렬

종목마다 거래정지·상장일이 달라 일자 배열이 어긋난다. 원 코드는 지수 달력에 맞추어
`reindex(...).ffill()` 로 정렬한다. 앱에는 지수 계열이 없으므로 **유니버스 전체 일자의
합집합을 달력으로 삼고 종목별로 직전 값을 채운다.** 채워 넣은 날에도 이동평균이 계속
정의되므로 시장폭이 끊기지 않는다.

### 6.4 응답 형식의 함정

`period` 명세에는 "`Output_0` 는 명세상 Array 인데 예시 응답은 Object" 라는 경고가 붙어 있다.
우리가 쓰는 것은 `Output_1`(일봉 배열)뿐이므로, `Output_0` 은 기존 `accounts()` 가 쓰는
방식대로 `JsonElement` 로 받아 넘긴다.

## 7 앱 구조에 붙는 방식

기존 경계를 하나도 바꾸지 않는다. `NhApi` 는 여전히 NH 를 아는 유일한 파일이고, 새 계산
코드는 네트워크를 모르는 순수 함수이며, 화면은 NH 필드명을 모른다.

| 파일 | 책임 |
|---|---|
| `market/Breadth.kt` | 순수 계산. 종가 배열에서 시장폭·백분위·평활·앙상블을 거쳐 목표·밴드·판정까지 |
| `market/MarketData.kt` | 유니버스·종가 캐시 파일과 `NhApi` 호출 오케스트레이션, 진행률 |
| `market/BandGuide.kt` | 밴드별 지침(정적 데이터)과 지침 화면 |
| `market/MarketCard.kt` | 포트폴리오 화면 상단 카드 |
| `api/NhApi.kt` | 메서드 2개 추가 (`etfComponents`, `dailyBars`) |
| `portfolio/PortfolioScreen.kt` | 카드 배치와 `applyMarketTarget()` |

목표 비중의 반영은 **이미 있는 함수 한 줄**로 끝난다.

```kotlin
// 모델 목표가 12.5% 이면 예수금 목표를 87.5% 로 잡는다.
// 종목끼리의 상대 비율은 그대로 두고 합계만 12.5% 가 되도록 비례 조정된다.
Rebalance.scaleForCash(targets, cashBp = FULL_BP - exposureBp, currentWeightsBp())
```

`scaleForCash` 는 되풀이해 불러도 누적 오차가 없도록 이미 설계되어 있어, 매주 목표가 바뀌어도
원본을 따로 보관할 필요가 없다. 최대잉여법으로 합계가 정확히 100% 가 되는 것도 기존 테스트가
보장한다.

## 8 화면 사양

1차 범위는 **판정 + 목표 적용 + 밴드 지침**이다. 2026-09-05 에 확정했다.

### 8.1 포트폴리오 화면 상단 카드

- 오늘의 판정 한 줄: "실행하지 않습니다" 또는 "비중을 X%로 줄입니다" 또는 "비중을 X%로 늘립니다".
- 모델 목표, **유지 비중**(§2.3), 차이(%p), 밴드 이름. 실제 주식 비중은 참고값으로 작게 붙인다.
  유지 비중이 없어 실제 비중과 비교했다면 그 사실을 한 줄로 적는다.
- 늘리는 판정이면 "3영업일 간격 3회 분할"을, 줄이는 판정이면 "당일 또는 익일에 한 번에"를
  판정 설명에 붙인다. 실행 추적은 1차 범위 밖이다.
- 기준 일자(마지막 거래일)와 경과 일수를 표시하고, 7일이 지나면 갱신을 권한다.
- 백분위 창이 756개를 채우지 못했으면 "백분위 창 N/756일" 을 붙인다(§2.2).
- "이 목표로 맞추기" 버튼을 누르면 `scaleForCash` 로 종목 목표가 비례 조정되고, 기존
  매수/매도 수량 계산이 그대로 갱신된다.
- 데이터가 모자라면 숫자 대신 "아직 계산할 수 없습니다 — 거래일 N, 최소 약 500일" 을 표시한다.

### 8.2 밴드 지침 화면

카드를 누르면 이동한다.

- 5개 밴드 카드를 세로로 배치하고 현재 밴드를 강조한다.
- 밴드마다 상태 설명, 해야 할 일, 하지 말아야 할 일, 검증 기간 관측값(체류 비율, 중앙
  지속일, 연환산 변동성, 3개월 내 ±10% 확률, 3개월 최악 사례)을 담는다.
- "이 신호가 알려 주지 않는 것"과 "절대 하지 않는 다섯 가지"를 접이식으로 넣는다.
- 관측값은 `guide.json` 산출물에서 옮긴 **정적 상수**다. 앱이 다시 계산하지 않는다. 값의
  출처와 검증 기간(2004-01-02 ~ 2026-09-04)을 화면 아래에 밝힌다.

### 8.3 갱신 동작

- 사용자가 누를 때만 실행한다. 자동 갱신도 백그라운드 작업도 없다.
- 최초 백필은 통신량을 미리 알리고 진행률을 보여 주며 중단 후 재개할 수 있어야 한다.
- 호출 간격은 0.25초 이상을 유지한다(초당 5회 제한). 429 는 지연만 하고 토큰을 건드리지 않는다.

## 9 실계좌·실기기로만 확인할 수 있는 미지수

착수 전에 확인해야 한다. 1번은 백필 설계 자체를 가른다.

1. **`period` 의 `array_cnt` 상한과 조회 가능 기간.** 명세는 길이 4 라고만 쓰여 있고 상한도
   과거 한계도 없다. 4년치를 받지 못하면 부분 창으로 계산되고(§2.2), **약 500일에도
   못 미치면 신호 자체가 나오지 않는다.** 건수를 자르되 `cts` 를 주지 않는 API 라면 `edate`
   를 옮겨 가며 수동으로 이어 받는다. `maxavg`(최대이평)를 함께 보내면 이평 계산용 추가
   봉을 더 주는지도 같이 확인한다.
2. **`etfComponents` 가 069500 에 대해 실제로 몇 종목을 주는가.** 상위 구성만 주는 API 일
   가능성이 있다. 200종목 전부가 아니면 유니버스가 대형주 쪽으로 더 치우친다.
3. **`period` 가 수정주가인가.** §6.1 의 보정은 두 경우 모두 옳게 동작하도록 설계했지만,
   실제로 어느 쪽인지 알아 두면 이상값을 만났을 때 원인을 빨리 좁힐 수 있다.
4. **`etfComponents` 와 `period` 가 `cts` 연속조회를 쓰는가.** 기존 `pages()` 가 그대로
   처리하지만, 쓰지 않는다면 호출 예산이 줄어든다.
5. ~~`riskmodel.py` 의 `score_to_exposure` 와 `_pct_rank`~~ — 2026-09-05 에 원 코드를 받아
   §2 에 반영했다(구성별 양자화 두 번, 은행가 반올림, `min_periods=252` 부분 창, 동점 평균
   순위). 남은 미지수가 아니다.

## 10 검토했으나 채택하지 않은 것 (기록)

| 선택지 | 채택하지 않은 이유 |
|---|---|
| KIS OpenAPI 의 시가총액 상위 랭킹 사용 | 유니버스 하나 때문에 두 번째 자격증명·토큰 경로·설정 화면·보안 문서 확장을 들여야 한다. ETF 구성종목이 같은 일을 호출 1회로 한다 |
| 종목코드 250개를 앱 자산으로 고정 | 검증값 재현은 가능하지만 분기 갱신이 사람 손에 묶여 유니버스가 낡아 간다 |
| 증분 갱신 상태기계(이동평균만 이어 붙이기) | 종가 1 MB 를 그대로 두고 매번 전체를 다시 계산하는 편이 더 빠르고, 옮길 상태가 없어 틀릴 곳도 없다 |
| 종가 이력을 `Vault` 로 봉인 | 공개 시장 데이터라 지킬 비밀이 없고, DEK 에 묶이면 저장 경로만 좁아진다 |
| Room·SQLite 도입 | 1 MB 짜리 배열 하나에 DB 엔진의 이점이 없다 |
| 시장폭 이력을 저장해 두고 이어 붙이기 | 유니버스가 바뀌면 과거와 현재가 다른 기준으로 섞인다. 원 코드처럼 매번 소급 계산하는 편이 일관된다 |
| 평활 워밍업을 0.5 로 채우기(`fillna(.5)`) | 백테스트 시작용 장치다. 실사용에서 쓰면 "모르는 상태"가 "비중 50%" 라는 지시로 둔갑한다 |
| 판정을 실제 주식 비중과 비교하기 | `backtest()` 는 마지막 실행 목표(`held`)와 비교한다. 실제 비중과 비교하면 드리프트만으로 검증된 것보다 두 배 가까이 자주 매매한다(§2.3) |
| `riskmodel.py` 의 여섯 신호 전부 이식 | 최종 모델은 `breadth` 하나다. 나머지는 보고서의 비교 전략이라 환율·S&P 데이터를 들일 이유가 없다 |
