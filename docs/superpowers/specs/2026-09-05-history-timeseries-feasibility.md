# 거래이력 저장과 시계열 차트 — 타당성 검토 (2026-09-05)

> **상태**: 검토 완료, 구현 미착수. 사용자 요청으로 조사만 수행했다.
>
> **요청 원문**: "선택한 계좌의 전체 거래이력을 암호화하여 DB에 저장하고 앱에서 시계열
> 자산변화와 수익률 변화를 표시하는 기능을 만들수 있는지 확인하여 검토 결과를 보여 주세요."
>
> **결론 한 줄**: 만들 수 있다. 다만 "전체 거래이력을 모아 과거 자산 추이를 그린다"는 접근은
> 이 API 에서 **가장 비싼 경로**이고, 과거 총자산은 **원리적으로 복원되지 않는다**.
> `dailyPnl` 1회 호출과 일별 스냅샷 1줄이 같은 화면을 훨씬 싸게 만든다.
>
> **근거 자료**: `https://www.nhplug.com/openapi-docs/{common,krstock,gbstock}/openapi.json`
> 및 `https://www.nhplug.com/llms-full.txt` 를 2026-09-05 에 내려받아 확인했다.
> krstock 31개 엔드포인트를 전수 확인했고, common 은 토큰 발급과 계좌목록 2개뿐이다.

## 1 판정 요약

| 요구사항 | 판정 | 핵심 근거 |
|---|---|---|
| 거래이력 전체 수집 | 가능하지만 비싸다 | 조회 API 가 **하루 단위**라 3년치에 약 750회 호출이 필요하다 |
| 암호화하여 저장 | 그대로 가능하다 | 기존 `Vault` 의 AES-256-GCM 을 재사용하면 새로 짤 암호 코드가 없다 |

| 수익률 변화 (평가손익 포함) | 지금부터만 정확하다 | 위의 자산 변화와 같은 제약을 받는다 |

## 2 API 조사 결과

### 2.1 쓸 수 있는 엔드포인트

| 엔드포인트 | 입력 (`*` 는 필수) | 얻는 것 |
|---|---|---|
| `krstock/inquiry/v1/dailyOrderExecution` | `orr_dt`* **단일 일자**, `act_no`*, `ost_cns_dit`* | 체결내역: `iem_cd`, `sby_dit_cd_nm`(매매구분), `tot_cns_qty`, `cns_avg_uit_pr`, `cns_amt`, `orr_tm`, `cfd_lon_cd`(신용대출코드) |
| `krstock/inquiry/v1/dailyPnl` | `act_no`*, `iqr_sta_dt`*~`iqr_end_dt`* **기간**, `iem_cd`(선택) | 일별(`sby_dt`) 매수·매도금액, `byn_fee`, `sll_tax_sum`, **`pls_amt`(손익금액), `pft_rt`(수익률)** |
| `krstock/inquiry/v1/tradingPnl` | `act_no`*, 기간 | 종목별 실현손익 누계, 수수료·세금 합계 |
| `krstock/inquiry/v1/assetStatus` | `act_no`*, `eal_aly_cd`*, `aet_bse`*, `qut_dit_cd`* (**날짜 입력 없음**) | 현재 `tot_aet_amt`(총자산), `nas_amt`(순자산), `tot_eal_amt`, `tot_eal_pls_amt`, `pft_rt` |
| `krstock/inquiry/v1/realizedPnl` | `act_no`*, `iqr_dit_cd1`*, `fee_dit_cd`*, `qut_dit_cd`* | `pft_rt1`(총수익률), `pft_rt3`(전일대비수익률), `bf_dd_eal_amt2`(전일평가금액) |
| `krstock/quote/v1/period` | `market_cd`*, `iem_cd`*, `gubun=1`(일), `edate`, `array_cnt` | 과거 일봉. `Output_1` 에 `bsop_date`, `stck_prpr`(종가) |
| `krstock/inquiry/v1/rightsHeld` | `act_no`*, `sta_dt`, `rit_tp_cd` | 권리 배정 내역. `rit_tp_cd` 에 **01.배당 02.유상 03.무상 07.ETF분배금 25.액면분할** 등. 응답에 `rit_aloc_amt`, `aloc_qty`, `aloc_amt_pym_dt`, `bse_dt` |

유량 제한은 문서에 **초당 5회 수준, 0.2초 이상 간격 권장**으로 명시되어 있다. 초과는 토큰
문제가 아니므로 재발급하면 안 된다.

### 2.2 없는 것: 입출금 내역 API

**국내주식에는 입금·출금·예수금 변동 이력을 돌려주는 API 가 하나도 없다.** common 은 토큰
발급과 계좌목록 둘뿐이고, krstock 31개를 전수 확인했으나 해당하는 것이 없다.

여기에 주목할 비대칭이 있다. **해외주식에는 정확히 필요한 API 가 존재한다.**

```
POST /gbstock/inquiry/v1/dailyTransaction   (해외주식 일별거래내역)
  입력: act_no*, iqr_sta_dt* ~ iqr_end_dt*,
        act_trd_cfc_cd* = 00.전체 01.입금 02.출금 03.입고 04.출고 05.매수 06.매도
  출력: trd_dt, trd_qty, trd_uit_pr,
        trd_bf_bnc_qty / trd_af_bnc_qty   (거래 전후 잔고수량)
        trd_bf_dca     / trd_af_dca       (거래 전후 예수금)
```

기간 조회에 입출금을 포함하고 거래 전후의 잔고와 예수금까지 실어 준다. 이 하나면 완전한
원장을 만들 수 있다. 그런데 국내주식에는 대응 API 가 없다. **향후 해외주식을 붙일 때는 이
기능이 오히려 국내주식보다 정확하게 구현된다**는 뜻이기도 하다.

## 3 요구사항별 상세

### 3.1 거래이력 전체 수집: 가능하지만 백필 비용이 크다

`dailyOrderExecution` 의 필수 입력은 `orr_dt` 한 날짜다. 기간 조회를 지원하지 않으므로
**조회하려는 날짜 수만큼 호출해야 한다.**

- 3년치는 약 750 영업일이므로 750회 호출이다. 0.2초 간격이면 최소 150초이고, 연속조회(`cts`)
  페이징과 여유를 감안하면 실제로 **4~6분**이 걸린다.
- 따라서 최초 1회만 수행하는 백필이어야 하고, 진행률 표시와 중단 후 재개를 갖추어야 하며,
  자동으로 다시 돌아서는 안 된다. 백필이 끝난 뒤의 증분은 하루 1회 호출로 끝난다.

한계가 둘 있다.

1. **수수료와 세금 필드가 없다.** 정확한 순손익은 `dailyPnl` 이나 `tradingPnl` 에서 따로
   받아 보완해야 한다.
2. 명세에 "`Output_0` 은 명세상 Object 인데 예시 응답은 Array" 라는 경고가 붙어 있다.
   기존 `accounts()` 가 쓰는 방식대로 `Output_0` 을 `JsonElement` 로 받아 넘기면 된다.

### 3.2 시계열 자산 변화: 앞으로는 정확하고 과거는 근사치다

특정 과거 시점 D 의 총자산에는 세 값이 필요하다.

```
총자산(D) = Σ(보유수량ᵢ(D) × 종가ᵢ(D)) + 예수금(D)
```

| 항목 | 조달 방법 | 판정 |
|---|---|---|
| 종가(D) | `quote/v1/period` 종목당 1회 호출 | **가능** |
| 보유수량(D) | 현재 잔고에서 그 이후의 순매수를 역산 | **조건부 가능.** 무상증자·액면분할·주식 입출고처럼 매매가 아닌 수량 변동이 있으면 어긋난다. `rightsHeld` 가 해당 권리를 코드별로 주므로 상당 부분 보정할 수 있다 |
| 예수금(D) | 없음 | **불가능.** 입금·출금·배당금 지급·이자를 알아야 복원되는데 §2.2 대로 API 가 없다 |

그러므로 과거를 소급해 그릴 수 있는 것은 **"주식 평가금액 추이"까지이고, "총자산 추이"는
정확도를 보장할 수 없다.** 반대로 오늘부터 하루에 한 줄씩 `assetStatus` 를 스냅샷으로
저장하면 그 이후의 총자산 추이는 완전히 정확하다.

### 3.3 시계열 수익률 변화: 실현손익은 저렴하고 평가손익은 앞으로만 정확하다

`dailyPnl` 은 계좌번호와 시작일·종료일만 필수이고 종목코드는 선택이다. 즉 **호출 한 번으로
지정한 기간 전체의 일별 매수금액·매도금액·수수료·세금·손익금액·수익률을 한꺼번에 받는다.**
750회 백필 없이 곧바로 "실현손익 추이" 차트를 그릴 수 있다.

다만 이것은 실현손익이므로 **매도한 날에만 값이 생긴다.** 보유 중인 평가손익까지 포함한
총수익률의 추이는 §3.2 와 같은 제약을 받아, 앞으로 쌓는 스냅샷으로만 정확해진다.

한 가지 더 짚어 둔다. 입출금을 모르므로 **엄밀한 시간가중수익률(TWR)은 계산할 수 없다.**
입금으로 인한 자산 증가와 수익으로 인한 자산 증가를 구분할 근거가 없기 때문이다. 근사치로
그리거나, 입출금 발생일을 사용자가 직접 표시하게 하는 방법 중에서 선택해야 한다.

### 3.4 암호화 저장: 그대로 가능하나 저장 위치는 분리해야 한다

암호화 자체는 새로 만들 것이 없다. `Vault` 의 `seal()`/`open()` 이 이미 AES-256-GCM 이고,
`store/Prefs.kt` 의 `accountKey()` 가 계좌번호를 SHA-256 으로 해싱해 키 이름에 계좌번호가
남지 않게 하는 규칙까지 갖추고 있다. 화면 캡처 차단(`FLAG_SECURE`)도 이미 걸려 있다.

**제약 하나를 반드시 지켜야 한다.** DEK 는 잠금이 풀린 동안에만 프로세스 메모리에 존재한다.
따라서 **동기화는 앱이 열려 있고 잠금이 해제된 동안에만 수행할 수 있으며, WorkManager 를
이용한 야간 자동 동기화는 구조적으로 불가능하다.** 이는 기존 "포그라운드 전용" 방침과 일치한다.

**저장 위치는 기존 DataStore 와 분리해야 한다.** DataStore Preferences 는 `edit {}` 한 번마다
파일 전체를 다시 쓴다. 지금 이 파일에는 비밀과 목표 비중이 들어 있고 토큰 재발급이나 목표
비중 수정 때마다 쓰기가 일어난다. 여기에 거래이력 blob 을 같이 넣으면 **상관 없는 설정 변경
한 번이 매번 그 전체를 다시 쓰게 된다.**

데이터 규모는 다음과 같다.

| 데이터 | 3년치 규모 |
|---|---|
| 일별 스냅샷 (일자·총자산·예수금·평가금액·누적실현손익) | 약 750줄, **30 KB** |
| 거래이력 (일반적인 계좌) | 수십 KB |
| 거래이력 (매우 활발한 계좌, 하루 20건) | 약 15,000줄, **1~2 MB** |

저장 방식은 셋 중에서 고른다.

| 방식 | 새 의존성 | 평가 |
|---|---|---|
| **월 단위로 나눈 봉인 파일** (`history/<계좌해시>/YYYYMM.bin`) | 없음 | 증분은 해당 월 파일만 다시 쓰고 기간 조회는 해당 월만 읽는다. 스키마도 마이그레이션도 없다. **권장** |
| 프레임워크 SQLite (`android.database.sqlite.SQLiteOpenHelper`) + 봉인 blob 컬럼 | 없음 | 안드로이드 기본 클래스라 의존성이 늘지 않고 날짜 범위 질의를 SQL 로 처리한다 |
| Room + SQLCipher | KSP 포함 4개 이상 | 투명한 DB 암호화를 얻지만, DB 가 전혀 없는 단일 모듈 앱에 과하다 |

위 규모에서는 DB 엔진이 주는 이점이 거의 없으므로 첫 번째를 권한다. 다만 "DB 에 저장" 이
SQLite 를 명시적으로 의도한 것이라면 두 번째도 의존성 추가 없이 가능하다.

## 4 권장 구현 순서

기능 전체를 한 번에 만들기보다 **가장 싼 것부터 단계로 나누는 편이 유리하다. 1단계만으로도
요청한 차트 두 개가 화면에 나온다.**

### 4.1 1단계: 백필 없이 차트 두 개 (권장 출발점)

- `dailyPnl` 을 **한 번** 호출해 일별 실현손익과 수익률 추이를 그린다.
- 잔고를 조회할 때마다 그날의 총자산·예수금·평가금액·누적 실현손익을 **한 줄로 봉인해
  저장한다.** 하루 한 줄이면 3년에 30 KB 다.
- 차트는 Compose Canvas 로 직접 그린다. 750개 점을 잇는 선 하나와 축이면 차트 라이브러리를
  새로 넣을 이유가 없다.

건드릴 곳은 `api/NhApi.kt` 에 메서드 하나, 저장소 파일 하나, 화면 하나이며 약 300줄이다.

### 4.2 2단계: 거래이력 백필

- 종목별 매매 내역을 한 건씩 열람하려는 요구가 실제로 확인된 뒤에 착수한다.
- 진행률 표시, 중단 후 재개, 자동 재실행 금지를 반드시 갖춘다.
- `rightsHeld` 를 함께 받아 배당과 무상증자를 별도 항목으로 남긴다.

### 4.3 3단계: 과거 소급 재구성

- `quote/v1/period` 의 종가와 2단계의 거래이력을 결합해 **"주식 평가금액 추이"만** 소급한다.
- 예수금을 복원할 수 없으므로 **총자산이 아니라는 점을 화면에 명시해야 한다.** 이 앱은
  사용자가 실제 돈으로 행동하는 숫자를 내놓는 것이 존재 이유이므로, 근사치를 정확한 값처럼
  보여 주어서는 안 된다.

## 5 실계좌로만 확인 가능한 미지수

착수 전에 반드시 확인해야 한다. `nh-portfolio-open-questions` 에 기록된 미해결 사항과 같은
성격이며, 1번은 요구사항 성립 여부 자체를 가른다.

1. **`dailyOrderExecution` 이 과거 몇 년까지 응답하는가.** 명세에 조회 가능 기간 제한이 적혀
   있지 않다. 국내 증권사 API 는 3개월에서 5년까지 편차가 크다. **3개월 제한이라면 "전체
   거래이력" 이라는 요구 자체가 성립하지 않는다.**
2. **`rightsHeld` 가 이미 매도한 종목의 과거 배당까지 돌려주는가.** 이름이 "권리보유" 이므로
   현재 보유분만 줄 가능성이 있다.
3. **`dailyPnl` 의 `pft_rt` 단위가 12.5 인지 0.125 인지.** 잔고 조회의 `pft_rt` 와 같은
   문제이며, 틀리면 화면의 수익률이 100배 어긋난다.
4. **`dailyOrderExecution` 의 `Output_0` 실제 타입.** 명세는 Object, 예시는 Array 로 다르다.

## 6 검토했으나 채택하지 않은 것 (기록)
